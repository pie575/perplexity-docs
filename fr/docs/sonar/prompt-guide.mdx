Les bonnes pratiques de prompting communes sont décrites dans le [guide de prompting de l&#39;Agent API](/fr/docs/agent-api/prompt-guide) et s&#39;appliquent à Sonar sans modification : soyez précis, limitez le nombre de résultats, ne demandez pas d&#39;URL en texte libre, évitez les contenus few-shot et privilégiez les paramètres plutôt que le texte pour les filtres.

Cette page traite de la seule différence structurelle qui change la manière de formuler les prompts pour Sonar : le prompt système n&#39;influence pas la recherche.

<div id="shape-search-through-the-user-message">
  ## Orienter la recherche via le message utilisateur
</div>

Sonar effectue une recherche web avant de générer sa réponse, et seul le message utilisateur alimente cette recherche. Le prompt système n&#39;est pas visible par la recherche : il n&#39;atteint le model qu&#39;au moment de la réponse, une fois les résultats déjà en main. Réservez le prompt système au ton, au style et aux règles d&#39;ancrage, et considérez le message utilisateur à la fois comme la question posée au model et comme l&#39;amorce de la recherche.

Conséquence pratique : la formulation du message utilisateur détermine directement les sources remontées. Une question précise et descriptive donne de meilleurs résultats qu&#39;une question vague, et un prompt système soigné ne rattrapera pas un message utilisateur imprécis. Si la qualité de la récupération compte, c&#39;est là qu&#39;il faut investir en premier.

**Bon exemple** : « Quelles orientations la FDA a-t-elle publiées sur l&#39;IA dans les dispositifs médicaux au cours de l&#39;année écoulée, et quelles catégories de dispositifs couvrent-elles ? »

**Mauvais exemple** : « Parle-moi des règles de la FDA sur l&#39;IA. »

<Warning>
  Ne placez pas d&#39;instructions de recherche dans le prompt système. Des formulations comme « cherche uniquement sur Wikipédia » ou « trouve les résultats les plus récents » n&#39;ont aucun effet. Pour des contraintes strictes telles que le domaine, la fraîcheur ou la région, utilisez les [paramètres de filtre de recherche](/fr/docs/sonar/filters) dédiés dans le corps de la requête plutôt que de formuler la contrainte en langage naturel.
</Warning>

<CodeGroup>
  ```python Python theme={null}
  from perplexity import Perplexity

  client = Perplexity()

  completion = client.chat.completions.create(
      model="sonar",
      messages=[
          {"role": "user", "content": "Summarize the FDA's regulatory framework for Software as a Medical Device (SaMD), including the Pre-Cert program."}
      ],
      search_domain_filter=["fda.gov"],
      search_recency_filter="month"
  )

  print(completion.choices[0].message.content)
  ```

Cela contraste avec l&#39;Agent API, où les `instructions` sont relues à chaque tour de la boucle de l&#39;agent et orientent aussi bien les appels d&#39;outils que la réponse finale. Dans Sonar, `instructions` n&#39;a pas d&#39;équivalent : les messages système influencent uniquement la génération, jamais la récupération.

<div id="reduce-hallucinations">
  ## Réduire les hallucinations
</div>

Les LLM sont réglés pour être serviables, ce qui les amène parfois à fournir une réponse lorsque les résultats de recherche sont maigres ou hors sujet, au lieu de signaler le manque d&#39;information. Le prompt système n&#39;influence pas l&#39;étape de recherche elle-même, mais il détermine la façon dont le modèle exploite les résultats lors de la rédaction de la réponse finale : c&#39;est donc le bon endroit où définir des règles d&#39;ancrage. Deux courts ajouts suffisent à couvrir la plupart de ces cas limites.

**Autorisez explicitement le modèle à dire qu&#39;il n&#39;a rien trouvé.** Avec une porte de sortie explicite dans le prompt système, le modèle est plus enclin à reconnaître l&#39;insuffisance des résultats qu&#39;à s&#39;appuyer sur ses données d&#39;entraînement pour combler le vide.

```text System Prompt theme={null}
Répondez uniquement à partir des résultats de recherche fournis. Si les résultats ne contiennent pas la réponse, dites-le explicitement au lieu de deviner.
```

**Exigez la mention des correspondances approximatives.** La recherche renvoie parfois des résultats proches mais non concordants (une année différente, une maison mère au lieu d&#39;une filiale, un produit similaire). Demander au modèle de signaler d&#39;emblée l&#39;écart évite que ces cas soient présentés comme des réponses directes.

```text System Prompt theme={null}
Si les résultats de recherche sont proches du sujet mais ne correspondent pas à la question (une autre année, une société mère ou un produit similaire), signale explicitement cet écart avant de répondre.
```

<div id="what-carries-over-from-the-agent-api-guide">
  ## Ce qui reste valable depuis le guide de l&#39;Agent API
</div>

Les mêmes règles fondamentales de rédaction de prompts s&#39;appliquent, sans changement :

* **Soyez précis et descriptif** dans le message utilisateur. Des requêtes vagues donnent des résultats dispersés.
* **Limitez le nombre de résultats.** Si une liste est nécessaire, précisez sa longueur.
* **N&#39;utilisez pas de few-shot sur le contenu.** Coller un exemple de réponse entièrement rédigé peut amener l&#39;étape de recherche à se focaliser sur le sujet de l&#39;exemple. Le few-shot sur la *structure* ne pose pas de problème ; pour garantir un format, utilisez `response_format`.
* **Ne demandez pas d&#39;URL dans le texte de la réponse.** Sonar renvoie toujours les sources dans les champs de premier niveau `citations` et `search_results`. C&#39;est là qu&#39;il faut les lire.
* **Utilisez des paramètres, pas de la prose, pour les filtres.** Le backend de recherche lit les paramètres ; il ne lit pas le prompt système.
