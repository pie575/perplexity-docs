<div id="overview">
  ## 概览
</div>

Pro Search 分类器是一套智能系统，可自动判断某个查询是需要 Pro Search 的高级多步工具调用，还是用标准的 Fast Search 即可有效作答。借助这一优化，你可以在性能需求与成本效率之间取得平衡。

<Info>
  你无需在 `"pro"` 和 `"fast"` 两种搜索类型之间手动选择，只需使用 `"auto"`，即可让分类器为每个查询做出最优决策。
</Info>

<div id="how-it-works">
  ## 工作原理
</div>

当你设置 `search_type: "auto"` 时，分类器会从多个维度分析你的查询：

<Steps>
  <Step title="查询复杂度分析">
    分类器会评估：

    * 子问题或涉及方面的数量
    * 是否需要进行对比分析
    * 是否需要多步推理
    * 所需信息综合的复杂程度

    ```json theme={null}
    {
      "web_search_options": {
        "search_type": "auto"  // 交由分类器决定
      }
    }
    ```
  </Step>

  <Step title="分类决策">
    分类器会根据分析结果，将查询路由到以下两者之一：

    * **Pro Search**：适用于需要多步工具调用的复杂、多层面查询
    * **Fast Search**：适用于简单直接的信息检索

    该决策会在响应元数据中透明呈现。
  </Step>

  <Step title="执行">
    所选的搜索模式会处理你的查询：

    * **Pro Search**：自动使用内置工具 (web&#95;search、fetch&#95;url&#95;content)
    * **Fast Search**：执行经过优化的单轮搜索与信息综合

    无论使用哪种模式，你都会得到同样高质量的响应格式。
  </Step>
</Steps>

<div id="classification-patterns">
  ## 分类模式
</div>

<div id="queries-classified-as-pro-search">
  ### 被归类为 Pro Search 的查询
</div>

适合通过多步工具调用来处理的复杂查询会被自动路由到 Pro Search：

<AccordionGroup>
  <Accordion title="多部分问题">
    **示例查询：**
    “React、Vue 和 Angular 在性能、学习曲线和生态系统方面有哪些差异？对于大型企业级应用，我应该选择哪一个？”

    **为何使用 Pro Search：**

    * 需要三个不同框架的相关信息
    * 需要跨多个维度进行对比分析
    * 涉及收集专家观点与建议
    * 需要综合多方来源的信息

    **工具调用：**

    * 针对每个框架进行多次网络搜索
    * 抓取 URL 以获取基准测试数据和官方文档
  </Accordion>

  <Accordion title="研究综述">
    **示例查询：**
    “总结关于间歇性断食对减重和代谢健康效果的最新同行评审研究，并包含样本量和研究局限性。”

    **为何使用 Pro Search：**

    * 需要查找多篇研究论文
    * 需要获取论文全文，而不仅是摘要
    * 涉及提取特定数据 (样本量、局限性)
    * 需要综合多项研究的结论

    **工具调用：**

    * 网络搜索近期的同行评审论文
    * 使用 `fetch_url_content` 阅读论文全文
    * 信息提取与综合
  </Accordion>

  <Accordion title="时效性强的复杂分析">
    **示例查询：**
    “分析美联储最近一次利率决议对股市的影响，包括对不同板块的影响以及专家对下一季度的预测。”

    **为何使用 Pro Search：**

    * 需要非常新的信息
    * 需要多来源交叉验证
    * 涉及逐个板块的分析
    * 需要汇总专家观点

    **工具调用：**

    * 多次有针对性的网络搜索
    * 抓取 URL 以获取金融分析报告
    * 综合多方专家观点
  </Accordion>
</AccordionGroup>

<div id="queries-classified-as-fast-search">
  ### 被归类为 Fast Search 的查询
</div>

无需多步推理的简单查询可由 Fast Search 高效处理：

<AccordionGroup>
  <Accordion title="简单事实性问题">
    **示例查询：**
    “法国的首都是哪里？”

    **为何使用 Fast Search：**

    * 单一且公认的事实
    * 无需计算或分析
    * 信息可直接从搜索摘要中获取

    **处理过程：**

    * 单次网络搜索
    * 直接从搜索结果给出答案
    * 无需多步推理
  </Accordion>

  <Accordion title="简单的信息检索">
    **示例查询：**
    “iPhone 15 Pro 的主要功能有哪些？”

    **为何使用 Fast Search：**

    * 单一产品查询
    * 信息可在产品说明中找到
    * 无需对比分析
    * 无需计算

    **处理过程：**

    * 搜索产品规格
    * 提取并列出功能
    * 基于搜索结果整合信息
  </Accordion>

  <Accordion title="单一主题查询">
    **示例查询：**
    “解释什么是机器学习。”

    **为何使用 Fast Search：**

    * 单一概念的定义
    * 无需多方面分析
    * 常规信息可直接获取

    **处理过程：**

    * 搜索机器学习的相关解释
    * 整合出清晰的定义
    * 引用可靠来源补充背景信息
  </Accordion>

  <Accordion title="基础定义类请求">
    **示例查询：**
    “API 是什么的缩写，它有什么用途？”

    **为何使用 Fast Search：**

    * 简单的定义请求
    * 无需复杂分析
    * 信息可直接获取

    **处理过程：**

    * 快速搜索 API 的定义
    * 解释该缩写及其基本用途
    * 给出清晰简洁的答案
  </Accordion>
</AccordionGroup>

<div id="pricing-comparison">
  ### 价格对比
</div>

**Pro Search 费率：**

* 输入：$3 / 100 万 token
* 输出：$15 / 100 万 token
* 请求费用：$14-$22 / 1,000 次请求 (取决于上下文大小)

**Fast Search 费率：**

* 输入：$3 / 100 万 token
* 输出：$15 / 100 万 token
* 请求费用：$6-$14 / 1,000 次请求 (取决于上下文大小，与标准 Sonar Pro 相同)

<Tip>
  自动分类器仅在确实需要 Pro Search 的高级能力时才会启用它，从而帮你节省成本，同时确保复杂查询依然能获得完整的多步工具调用。
</Tip>

  ### 使用自动分类

<CodeGroup>
  ```python Python SDK theme={null}
  from perplexity import Perplexity

  client = Perplexity()
  # 交由分类器决定
  response = client.chat.completions.create(
      model="sonar-pro",
      messages=[
          {
              "role": "user",
              "content": "Compare the energy efficiency (kWh/100mi and MPGe) of the Tesla Model 3, Chevrolet Bolt, and Nissan Leaf using EPA data."
          }
      ],
      stream=True,
      web_search_options={
          "search_type": "auto"  # 自动分类
      }
  )

  for chunk in response:
      if chunk.choices[0].delta.content:
          print(chunk.choices[0].delta.content, end="")
  ```

  ```typescript Typescript SDK theme={null}
  import { Perplexity } from '@perplexity-ai/sdk';

  const client = new Perplexity();

  // 交由分类器决定
  const response = await client.chat.completions.create({
    model: 'sonar-pro',
    messages: [
      {
        role: 'user',
        content: 'Compare the energy efficiency (kWh/100mi and MPGe) of the Tesla Model 3, Chevrolet Bolt, and Nissan Leaf using EPA data.'
      }
    ],
    stream: true,
    web_search_options: {
      search_type: 'auto'  // 自动分类
    }
  });

  for await (const chunk of response) {
    if (chunk.choices[0]?.delta?.content) {
      process.stdout.write(chunk.choices[0].delta.content);
    }
  }
  ```

<div id="manual-override">
  ### 手动覆盖
</div>

当你明确知道自己需要什么时，仍然可以手动指定搜索类型：

<Tabs>
  <Tab title="强制使用 Pro Search">
    当你确定需要多步工具调用时使用：

    ```python theme={null}
    response = client.chat.completions.create(
        model="sonar-pro",
        messages=[{"role": "user", "content": "Your complex query"}],
        stream=True,
        web_search_options={
            "search_type": "pro"  # 强制使用 Pro Search
        }
    )
    ```

    **手动指定 Pro 的适用场景：**

    * 你确定该查询需要多步推理
    * 自动分类结果为 Fast，但你需要更深入的分析
    * 关键查询，希望获得最强能力
  </Tab>

  <Tab title="强制使用 Fast Search">
    当你希望优化速度与成本时使用：

    ```python theme={null}
    response = client.chat.completions.create(
        model="sonar-pro",
        messages=[{"role": "user", "content": "Your simple query"}],
        stream=True,
        web_search_options={
            "search_type": "fast"  # 强制使用 Fast Search（也可省略，fast 为默认值）
        }
    )
    ```

    **手动指定 Fast 的适用场景：**

    * 简单查询，使用 Pro Search 属于大材小用
    * 对成本敏感的应用
    * 响应速度至关重要的场景
  </Tab>
</Tabs>

<div id="best-practices">
  ## 最佳实践
</div>

<Steps>
  <Step title="默认使用自动分类">
    对于大多数应用，建议使用 `search_type: "auto"`，交由分类器自动优化：

    ```python theme={null}
    web_search_options={"search_type": "auto"}
    ```

    这样既能为每个查询匹配合适的工具，又能控制成本。
  </Step>

  <Step title="监控分类模式">
    跟踪哪些查询被归类为 Pro、哪些被归类为 Fast，以了解自身的使用模式：

    * 复查那些始终走 Pro Search 的查询
    * 找出可在适当情况下改写为适合 Fast Search 的查询
    * 了解哪些用户问题确实需要高级能力

    这有助于优化应用中的查询设计。
  </Step>

  <Step title="有策略地使用手动覆盖">
    仅在以下情况下覆盖分类器：

    * 有特定的性能要求
    * 需要测试并对比 Pro 与 Fast 的结果
    * 构建复杂度已知的功能

    **示例：**

    ```python theme={null}
    # 已知为复杂分析——强制使用 Pro
    if query_requires_calculations(user_query):
        search_type = "pro"
    else:
        search_type = "auto"
    ```
  </Step>

  <Step title="有效地设计查询">
    合理组织查询结构，帮助分类器做出最优判断：

    **不够理想：**
    “介绍一下电动汽车”

    **更好：**
    “电动汽车的平均续航里程是多少？” (适合 Fast Search)

    **或者：**
    “对比 Tesla Model 3、Chevrolet Bolt 和 Nissan Leaf 五年内的总拥有成本，包括折旧、电费和维护费用” (适合 Pro Search)

    查询越清晰具体，分类效果越好。
  </Step>
</Steps>

<div id="common-questions">
  ## 常见问题
</div>

<AccordionGroup>
  <Accordion title="分类器的准确度如何？">
    分类器基于数千种查询模式训练而成，准确度很高。遇到任何模棱两可的情况时，它会倾向于选择 Pro Search，确保不会牺牲功能。

    不过，如果你发现分类持续出错：

    * 将查询改写得更具体
    * 对这类查询使用手动覆盖
    * 结合自身用例的具体需求进行权衡
  </Accordion>

  <Accordion title="我能查看实际使用了哪种模式吗？">
    可以，响应中的元数据会显示：

    * 使用了哪种搜索类型
    * 做出该分类的原因 (使用 auto 时)
    * 按搜索类型划分的费用明细

    这有助于你了解并优化自己的使用方式。
  </Accordion>

  <Accordion title="自动分类会增加延迟吗？">
    不会。分类在查询处理开始前的几毫秒内即可完成，不会对响应时间产生实质影响。分类器针对实时决策做了专门优化。
  </Accordion>

  <Accordion title="如果我不认同分类结果怎么办？">
    你随时可以使用手动覆盖：

    ```python theme={null}
    web_search_options={"search_type": "pro"}  # 强制使用你偏好的模式
    ```

    如果你经常不认同分类结果，可以考虑：

    * 让查询更加具体
    * 对这类查询使用手动覆盖
    * 重新评估你的用例是否需要固定使用 Pro 或 Fast 模式
  </Accordion>
</AccordionGroup>
