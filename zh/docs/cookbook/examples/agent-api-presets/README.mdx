title: "自定义 preset"
---

模型、工具和各项能力都在快速演进。要让智能体代码始终保持最契合自身用例的配置，几乎得投入全职精力。这正是 Perplexity preset 要解决的问题。

<div id="start-from-a-preset">
  ## 从 preset 开始
</div>

preset 是由 Perplexity 维护的一组 Agent API 设置，它将 model、搜索配置、推理步骤、system prompt 以及可用工具打包在一起。随着评估效果的提升，Perplexity 会持续更新底层配置，你的调用无需改动代码即可获得这些更新。

如果所选的 preset 不能完全满足需求怎么办？比如，你找到了一个几乎完全契合需求的 preset 配置，只是有一两个字段想要微调。这时可以按名称传入该 preset，然后只修改需要调整的字段，其余字段仍沿用 preset 的默认值。

<div id="check-the-prerequisites">
  ## 检查前置条件
</div>

你需要 Python 3.10 或更高版本，安装 `perplexityai` 库，并将 API key 导出为 `PERPLEXITY_API_KEY` 环境变量。可在 [console.perplexity.ai/group/keys](https://console.perplexity.ai/group/keys) 创建 key。如果你从未调用过该 API，请先完成 [Perplexity API 快速入门](https://docs.perplexity.ai/docs/getting-started/quickstart)。

```bash theme={null}
pip install perplexityai
export PERPLEXITY_API_KEY="pplx-..."
```

<div id="run-a-basic-example">
  ## 运行一个基础示例
</div>

除非另有说明，本教程中的所有示例均使用 `low` preset。先从只传入一个提示词的调用开始。

```python theme={null}
from perplexity import Perplexity

client = Perplexity()

response = client.responses.create(
    preset="low",
    input="Summarize the current Perplexity Agent API pricing page.",
)

print("model:", response.model)
print(response.output_text)
```

`low` preset 已提供 model、搜索配置、推理步骤、system prompt 和可用工具，你的请求只需提供输入内容。

<div id="customize-a-preset-in-two-moves">
  ## 两步定制 preset
</div>

两种技巧几乎能覆盖所有实际的定制需求：覆盖顶层字段，以及调整某个工具的选项。最后一节将介绍如何查看实际运行的配置。

<div id="1-override-one-parameter">
  ### 1. 覆盖单个参数
</div>

当 preset 基本合适、只有某个字段需要调整时，可以覆盖该参数。只需在请求中传入该字段，其余字段仍保持默认值。

`low` 的 `max_steps` 默认值较低 (具体数值请查阅最新的 preset 文档) 。当任务需要更多推理或工具调用迭代时，可调高这一上限：

```python theme={null}
response = client.responses.create(
    preset="low",
    input="Summarize this week's Agent API changelog.",
    max_steps=8,
)

print("model:", response.model)
print("status:", response.status)
print("tool invocations:", response.usage.tool_calls_details)
```

<div id="2-adjust-options-for-one-tool">
  ### 2. 调整某个工具的选项
</div>

如果 preset 的工具集本身适合当前任务，只有某个工具需要微调，那么调整该工具的选项即可。只需为该工具传入一份局部配置，preset 中的其他工具会继续保留。

当提示词中出现 URL 时，`low` 默认会调用 `fetch_url`。即使传入局部的 `web_search` 覆盖配置，`fetch_url` 仍会照常运行：

```python theme={null}
response = client.responses.create(
    preset="low",
    input=(
        "Read https://docs.perplexity.ai/docs/agent-api/presets "
        "and list the preset names on that page."
    ),
    tools=[{
        "type": "web_search",
        "max_tokens": 6000,
        "max_tokens_per_page": 1200,
    }],
)

print("model:", response.model)
print("tools ran:", list(response.usage.tool_calls_details.keys()))
```

2026 年 8 月 19 日使用 `perplexityai==0.43.3` 的实际运行结果：

```text theme={null}
model: openai/gpt-5.6-luna
tools ran: ['fetch_url']
```

该请求调整的是 `web_search`，但实际运行的却是 `fetch_url`，因为提示词要求读取某个 URL，而 `fetch_url` 正是完成这项工作的工具。证据就在 `usage.tool_calls_details` 中：尽管请求从未传入 `fetch_url` 条目，它仍然出现在了那里。这就是工具合并。若要一并调整 `fetch_url`，请在 `tools` 中除 `web_search` 之外再添加一个 `fetch_url` 条目。

<div id="put-both-moves-together-an-evidence-based-rollout-decision">
  ## 两种手法结合：基于证据的上线决策
</div>

下面把这些概念串联起来。假设某个 CPU 密集型服务的性能负责人正在评估是否试点 Python 3.14 的自由线程构建。`low` 是不错的基线，但这个任务需要更大的推理空间 (一次覆盖设置) ，以及来自两个特定技术页面的更深入上下文 (一次工具合并) 。

```python theme={null}
from perplexity import Perplexity

client = Perplexity()

response = client.responses.create(
    preset="low",
    input=(
        "You are the performance lead for a CPU-bound fraud-scoring service. "
        "The team proposes piloting Python 3.14's free-threaded build in "
        "production. Create an adoption brief of at most 450 words with exactly "
        "these Markdown headings: ## Decision, ## Three technical risks, "
        "## Five benchmark gates, and ## Two stop conditions. Make each list "
        "match the number in its heading. For every risk, separate the "
        "documented behavior from its implication for this service. Use only "
        "the sources allowed by the web_search tool. Cite factual claims inline "
        "using numeric result IDs, one source per bracket, like [1][2]. Never "
        "invent citation IDs. Do not include shell commands."
    ),
    max_steps=8,
    tools=[{
        "type": "web_search",
        "search_context_size": "high",
        "filters": {
            "search_domain_filter": [
                "docs.python.org/3.14/whatsnew/3.14.html",
                "docs.python.org/3/howto/free-threading-python.html",
            ],
        },
    }],
)

print(response.output_text)

print("\n--- Observed run ---")
print("model:      ", response.model)
print("status:     ", response.status)
print("tools:      ", response.usage.tool_calls_details)
print("total cost: $", response.usage.cost.total_cost)
```

调用中的每一部分都有各自的职责：

| 关注点                                        | 提供方                               |
| ------------------------------------------ | --------------------------------- |
| 已维护的 model、system prompt、推理设置、默认值及未公开列出的工具 | `low` preset                      |
| 应用任务与输出约定                                  | `input`                           |
| 额外的推理空间                                    | `max_steps=8` 覆盖                  |
| 更深入的证据提取                                   | `search_context_size="high"` 工具合并 |
| 可信来源策略                                     | URL 级 `search_domain_filter` 工具合并 |
| 运行时证据                                      | 响应元数据                             |

2026 年 8 月 19 日使用 `perplexityai==0.43.3` 进行的一次典型实际运行，生成了如下简报 (`response.output_text`) ：

```markdown theme={null}
## 决策

在生产环境中试点 Python 3.14 的自由线程（free-threaded）构建时，只能作为范围严格受限的金丝雀发布，而不能作为默认运行时。Python 3.14 已正式支持自由线程，但该特性仍是可选的；第三方扩展的兼容性以及特定工作负载下的扩展表现仍存在实质性的不确定性。[1][2] 在扩大流量之前，必须先具备启用 GIL 的回滚路径、完全一致的容量管控措施，并通过下述基准测试门槛。

## 三项技术风险

1. **已记录的行为：** 自由线程执行会引入单线程开销：在 `pyperformance` 各项测试中约为 1-8%，具体取决于平台与硬件。[2] **影响：** 即使多线程吞吐量有所提升，以串行 Python 为主的欺诈检测请求仍可能变慢，或消耗更多 CPU。

2. **已记录的行为：** 部分 C 扩展尚未适配自由线程运行，导入时可能自动重新启用 GIL，并输出一条警告。[2] **影响：** 服务中本应并行的工作进程可能悄然退化为串行执行，使吞吐量和尾延迟的测试结果具有误导性。请审计每一个依赖项，一旦 GIL 被意外重新启用，即判定试点失败。

3. **已记录的行为：** 内置容器提供了类似 GIL 时代的保护机制，但共享迭代器通常并非线程安全，并发访问帧还可能导致解释器崩溃。[2] **影响：** 特征提取、缓存或模型管道中现有的“有 GIL 所以安全”的假设，可能引发竞态、结果损坏或进程崩溃。应将共享可变状态一律视为需要显式同步。

## 五项基准测试门槛

1. **正确性：** 使用具有生产代表性的流量回放与 GIL 构建做对比；要求欺诈判定、评分、错误分类和审计记录完全一致。

2. **吞吐量：** 在目标核心分配和真实线程数下，持续每秒请求数至少要达到 GIL 构建的 1.20 倍。

3. **延迟：** 在峰值负载下的 p50、p95 和 p99 分位，退化不得超过 5%，且服务级目标零违约。

4. **CPU 效率：** 在同等流量下，每次评分请求的 CPU 秒数至少降低 10%；并单独测量工作进程增加时的扩展表现，因为自由线程并不会自动让每个程序受益。[2]

5. **运行安全性：** 使用生产环境的依赖版本进行 24 小时浸泡测试；要求零崩溃、零死锁、零数据竞态、零意外的 GIL 重新启用警告，且内存增长不超过与 GIL 构建约定的预算。自由线程构建通常会占用更多内存。[2]

## 两项终止条件

1. **立即回滚：** 若正确性出现差异、SLO 被突破、发生崩溃或死锁，或生产路径中任何依赖项重新启用了 GIL，立即停止试点并回退到 GIL 构建。

2. **试点后不予推进：** 若任一基准测试门槛未通过，则不得将部署范围扩大到金丝雀之外，尤其是吞吐量收益不足以抵消已记录的单线程开销，或内存/容量成本超出批准预算的情况。
```

<div id="inspect-what-actually-ran">
  ## 查看实际运行情况
</div>

你需要一种方式来确认 API 实际执行了什么：读取 `response.model` 可获知实际使用的 model，`response.usage.tool_calls_details` 可获知实际调用的工具，`response.usage.cost.total_cost` 可获知计费金额。响应中不会返回实际生效的 system prompt、`max_steps`、推理过程或完整的继承工具集，因此这只能用于查看本次运行的实际情况，而非 preset 的配置。

```python theme={null}
def inspect(preset: str, prompt: str) -> None:
    response = client.responses.create(preset=preset, input=prompt)
    print(f"preset={preset}")
    print(f"  model:       {response.model}")
    print(f"  status:      {response.status}")
    print(f"  invocations: {response.usage.tool_calls_details}")
    print(f"  total_cost:  ${response.usage.cost.total_cost}")

inspect("low", "Summarize the current Perplexity Agent API pricing page.")
```

你得到的数值会有所不同。以下是 2026 年 8 月 19 日使用 `perplexityai==0.43.3` 的实际运行结果：

```text theme={null}
preset=low
  model:       openai/gpt-5.6-luna
  status:      completed
  invocations: {'fetch_url': ToolCallDetailsOutput(invocation=1), 'search_web': ToolCallDetailsOutput(invocation=1)}
  total_cost:  $0.01812
```

对于任何看重正确性或成本的请求，都可以查看其实际执行情况：哪个 model 处理了该调用、运行了哪些工具，以及本次调用的成本。

<div id="summary">
  ## 小结
</div>

preset 为你提供一份可按名称调用、持续维护的 Agent API 配置。只需覆盖单个字段，就能改动其中一项设置，而不影响其他默认值。合并工具选项则可以在调整某个工具的同时，保留 preset 中已挂载的其他可用工具。读取 `response.model` 和 `response.usage.tool_calls_details` 即可查看调用详情。
