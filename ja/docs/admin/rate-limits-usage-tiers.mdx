<div id="what-are-usage-tiers">
  ## 利用ティアとは
</div>

利用ティアは、APIの累計利用額に応じて、**レート制限**と**ベータ機能**へのアクセス可否を決定するものです。APIクレジットへの支出が積み重なるにつれ、自動的に上位ティアへ移行し、レート制限が引き上げられます。上位ティアでは1分あたりのリクエスト数が大幅に増加し、一度到達したティアは降格されることなく永続的に維持されます。

<Info>
  現在の利用ティアは、APIコンソールの[料金ページ](https://console.perplexity.ai/project/pricing?tab=usage-tiers)で確認できます。
</Info>

***

<div id="tier-progression">
  ## ティアの進行
</div>

| ティア        | 購入クレジット総額 | ステータス            |
| ---------- | --------- | ---------------- |
| **ティア 0** | $0        | 新規アカウント、アクセス制限あり |
| **ティア 1** | $50以上     | 少量の利用、基本的な制限     |
| **ティア 2** | $250以上    | 通常の利用            |
| **ティア 3** | $500以上    | 大量の利用            |
| **ティア 4** | $1,000以上  | 本番環境での利用         |
| **ティア 5** | $5,000以上  | エンタープライズ利用       |

<Note>
  ティアは、現在の残高ではなく、アカウントの全期間における**累計購入額**に基づいて決定されます。
</Note>

***

<div id="router-api-rate-limits">
  ## Router API のレート制限
</div>

Router API へのリクエストにはレート制限が適用されます。リクエストがレート制限に達した場合、またはアップストリームの model が過負荷の場合、API は `Retry-After` ヘッダーを付与した `429` を返します。指定された間隔をあけてから再試行してください。

<Note>
  `429` で拒否されたリクエストは課金されません。
</Note>

***

<div id="agent-api-rate-limits">
  ## Agent API のレート制限
</div>

Agent API は各リクエストに対して、API 全体の QPS 制限と Agent モデルの 1 分あたりのリクエスト数 (RPM) 制限という 2 つの独立した制限を適用します。リクエストは、その両方の制限内に収まっている必要があります。なお、RPM の値は QPS の値から算出されるものではありません。

|     ティア    | QPS (1 秒あたりのクエリ数)  | 1 分あたりのリクエスト数 |
| :--------: | :----------------: | :-----------: |
| **ティア 0** |        1 QPS       |      50/分     |
| **ティア 1** |        3 QPS       |     150/分     |
| **ティア 2** |        8 QPS       |     500/分     |
| **ティア 3** |       17 QPS       |    1,000/分    |
| **ティア 4** |       33 QPS       |    4,000/分    |
| **ティア 5** |       33 QPS       |    8,000/分    |

<div id="search-api-rate-limits">
  ## Search API のレート制限
</div>

Search API には、すべての利用ティアに共通して適用される独自のレート制限があります。

| エンドポイント        | レート制限          | バースト容量    |
| -------------- | -------------- | --------- |
| POST `/search` | 1秒あたり50クエリユニット | 50クエリユニット |

**検索レートリミッターの動作:**

* **単一クエリのリクエスト**: 1クエリユニットを消費
* **複数クエリのリクエスト**: 配列内のクエリ1件につき1クエリユニットを消費
* **バースト**: 50クエリユニットを一度に消費可能
* **持続**: 平均で1秒あたり50クエリユニット

<Info>
  課金とレート制限では単位が異なります。5つのクエリを含むリクエストが成功した場合、課金上は Search API リクエスト1回ですが、レート制限上は5ユニットを消費します。検索のレート制限は利用ティアに依存せず、同じリーキーバケットアルゴリズムに基づいてすべてのアカウントに一貫して適用されます。課金の詳細については [Search API の料金](/ja/docs/getting-started/pricing#search-api-pricing) を参照してください。
</Info>

<div id="embeddings-api-rate-limits">
  ## Embeddings API のレート制限
</div>

Embeddings API では、利用ティアに応じて上限が変わるティアベースのレート制限を採用しています。各リクエストはエラスティックなバックエンド上での 1 回のフォワードパスで完結するため、他の API よりも上限が高く設定されています。

|      ティア      | QPS (1秒あたりのクエリ数)  |
| :-----------: | :---------------: |
|   **ティア 0**  |       85 QPS      |
| **Tiers 1–3** |      170 QPS      |
| **Tiers 4–5** |      335 QPS      |

<div id="contextualized-embeddings">
  ### コンテキスト付き埋め込み
</div>

コンテキスト付き埋め込みには、独立した、より高い上限が設定されています (標準の埋め込みティアの5倍) 。

|      ティア      | QPS (1秒あたりのクエリ数)  |
| :-----------: | :---------------: |
|   **ティア 0**  |      415 QPS      |
| **Tiers 1–3** |      835 QPS      |
| **Tiers 4–5** |     1,670 QPS     |

<Note>
  コンテキスト付き埋め込みのレート制限は、リクエスト数ではなく**チャンクの総数**に基づきます。
</Note>

<div id="how-rate-limiting-works">
  ## レート制限の仕組み
</div>

Perplexityのレート制限システムは**リーキーバケットアルゴリズム**を採用しており、長期的には厳格なレート制御を維持しつつ、バースト的なトラフィックにも対応できます。

<div id="technical-implementation">
  ### 技術的な実装
</div>

<AccordionGroup>
  <Accordion title="リーキーバケットアルゴリズムの解説">
    リーキーバケットアルゴリズムは、底に小さな穴が空いたバケツのように動作します。

    * **バケツの容量**: 即座に送信できるリクエストの最大数 (バースト容量)
    * **漏出レート**: バケツから token が漏れ出す速さ (レート制限)
    * **token の補充**: レート制限に応じて、一定間隔で token が継続的に補充されます

    この設計により、必要なときには正当なバーストトラフィックを許容しつつ、継続的な乱用を防ぎ、すべてのユーザーに対して予測可能で公平なレート制御を実現します。
  </Accordion>

  <Accordion title="レートリミッターの動作例">
    **毎秒 50 リクエスト**が実際にどのように動作するか見てみましょう。容量が 50 token、漏出レートが毎秒 50 token の場合、20ms ごとに 1 token が補充されます。

    **シナリオ 1: バーストトラフィック**

    ```
    時刻 0.0s: バケツは満杯（50 token）
    → 50 リクエストを即座に送信 → すべて許可
    → 51 番目のリクエストを送信 → 拒否（バケツが空）

    時刻 0.020s: 1 token 補充
    → 1 リクエスト送信 → 許可
    → 2 番目のリクエスト送信 → 拒否

    時刻 0.040s: さらに 1 token 補充
    → 1 リクエスト送信 → 許可
    ```

    **シナリオ 2: 一定の 50 QPS**

    ```
    20ms ごとにリクエスト:
    時刻 0.0s: リクエスト → 許可（50→49 token）
    時刻 0.020s: リクエスト → 許可（49+1-1=49 token）
    時刻 0.040s: リクエスト → 許可（49+1-1=49 token）
    ... 49〜50 token を維持し、すべてのリクエストが通過
    ```

    **シナリオ 3: 50 QPS をわずかに超える場合**

    ```
    19ms ごとにリクエスト（約 52.6 QPS）:
    → やがて補充より速く token が消費される
    → 一部のリクエストが拒否され始める
    → 平均ではちょうど 50 QPS に収まる
    ```
  </Accordion>

  <Accordion title="実運用での意味">
    リーキーバケット設計では、レート制限の上限分を一度に処理できるため、バッチ処理や急激なトラフィック増加に最適です。バースト容量に余裕がある場合、リクエストを意図的に分散させる必要はありません。

    このシステムは、長期的には平均レート制限を厳格に適用しつつ、バースト使用後の迅速な回復を可能にします。これにより、さまざまな利用パターンで一貫した性能が得られ、公平なリソース配分を保ちながら継続的な上限超過を防ぎます。

    アプリケーションを構築する際は、バッチ処理でバースト容量を活用し、リクエストのタイミングを最適化するために利用パターンを監視し、429 レスポンスに対する適切なエラーハンドリングを実装してください。
  </Accordion>
</AccordionGroup>

<div id="what-happens-when-you-hit-rate-limits">
  ## レート制限に達すると何が起こるか
</div>

レート制限を超過した場合:

1. **429 エラー** - リクエストが「Too Many Requests」として拒否されます
2. **継続的な補充** - レート制限に応じて token が継続的に補充されます
3. **即時の回復** - token が補充され次第、新しいリクエストを送信できるようになります

**回復時間の例:**

* **50 QPS 制限**: 20ms ごとに token が 1 個補充される
* **500 QPS 制限**: 2ms ごとに token が 1 個補充される
* **1,000 QPS 制限**: 1ms ごとに token が 1 個補充される

<Tip>
  **ベストプラクティス:**

  * 使用状況を監視し、上位ティアが必要になる時期を予測する
  * 本番アプリケーションでは、あらかじめティアのアップグレードを検討する
  * コードにジッター付きの指数バックオフを実装する
  * バッチ処理ではバースト容量を活用する
  * バースト容量に余裕がある場合は、リクエストを不必要に分散させない
</Tip>

<div id="upgrading-your-tier">
  ## ティアのアップグレード
</div>

<Steps>
  <Step title="現在のティアを確認する">
    APIコンソール で [Usage tiers](https://console.perplexity.ai/project/pricing?tab=usage-tiers) を開き、現在のティアと各ティアの購入しきい値を確認します。
  </Step>

  <Step title="クレジットを追加購入する">
    請求セクションからアカウントにクレジットを追加します。支出額がしきい値に達すると、ティアは自動的にアップグレードされます。
  </Step>

  <Step title="アップグレードを確認する">
    新しいレート制限は、ティアのアップグレード後ただちに適用されます。設定ページで確認してください。
  </Step>

  <Step title="さらに高い上限が必要な場合">
    ティア 5 を超えるカスタムレート制限が必要な場合は、[レート制限引き上げリクエストフォームにご記入ください](https://perplexity.typeform.com/to/yctmfyVT)。ユースケースを確認のうえ、ご要望に対応いたします。
  </Step>
</Steps>

<Check>
  上位ティアではレート制限が引き上げられ、API の利用体験が大幅に向上します。特に本番環境のアプリケーションでは重要なポイントです。
</Check>
